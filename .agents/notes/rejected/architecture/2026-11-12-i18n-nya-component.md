# Agent Note: 通用多语言模块与可选 Nya 组件适配

Status: rejected — 本阶段不采用预先建设通用模块及 Nya 适配，先做宿主与单应用试点。

用户于 2026-11-12 确认先不做 Nya 组件。当前主要消费者不运行 Nya，已有 mount/dispose 足以持有资源；来源服务的依赖撤销还可能把偏好失败扩大为界面重装。下文保留原候选供追溯，现行安排见[试点优先方向](../../proposed/architecture/2026-11-12-i18n-pilot-first.md)。未来若出现实际 Nya 消费者，需另建提议重新证明收益，不将本候选作为必交付后续阶段。

## 问题

用户已接受由宿主和应用各自负责自身多语言的方案，进一步提出能否像 Models 一样，将跨应用共用的多语言机制做成通用 NyaCore 组件。此前方案建议纯运行库，并排除了新增 Nya 组件；该限制没有区分纯格式化与有状态呈现实例的生命周期装配。

## 方向

建议演进为独立的通用多语言模块：便携核心提供独立实例、词条解析、语言协商、格式化缓存与变更订阅；可选 `/nya` 入口将同一核心适配为 Nya 组件，通过 inject 使用来源快照，并以 Effect 释放实例、来源订阅和消费者监听。它属于 Nya 生态模块，不要求修改 `@nya/core` 框架；可先像 Models 一样位于 Anybox 的独立 workspace 包。

组件定义可复用，实例按呈现所有者独立。已有同一根中多次安装须使用不同服务名，不创建额外应用 Context，也不以 appId 作为权限凭证。宿主偏好仍只通过数据契约传递，字典和实际语言归各应用。语言变化使用实例内部状态与通知，不调用 Fiber 更新/重启或重新注册服务。普通业务执行根不因 UI 多语言而增加语言状态；多客户端的 locale 不共享。

当前 Anybox 浏览器没有 Nya 根，仅共享 application-api/web；因此直接用相同便携核心并交由 mount/dispose 管理，不为翻译额外建立根。Nya 适配在存在真实 Nya 消费者时接入和验收；本轮只细化候选设计，未创建包、组件、服务或测试入口。用户已确认应用自有方案，尚未把本轮组件细节视为已批准实施。

本提议原用于评估[早期方向](../../proposed/architecture/2026-11-12-i18n-governance.md)中“不新增 Nya 组件”的限制；现由试点优先方向取代。应用资源归属、可选接入及受信执行边界继续适用。

## 备选方案

- 只提供纯函数库：足以完成查词与格式化，但已有 Nya 消费者仍需重复编排来源订阅和实例清理；保留为便携入口，不排除薄组件适配。
- 宿主安装一个全局翻译中心：会混合应用词条和多个查看者的语言状态，不采用。
- 只实现 Nya 组件，并给每个 Web 应用新增根：当前没有对应浏览器装配和验收，也与项目根约定不符，不采用。
- 照搬 Models 的存储、Vault、协议、来源目录与任务体系：多语言首期没有这些资源需求，不预建。

## 影响与代价

后续会增加组件适配及同核心两条装配路径的验证，但不重复实现翻译引擎。共享的是实现和公共类型，实例、字典、订阅及发布责任仍独立。NyaCore 源码未见明显 Node 原生运行依赖，但当前发布说明以 Node 为准，且没有找到浏览器验收；不能据此宣称浏览器兼容已完成。组件化不新增恶意应用的安全隔离。

## 验证

已只读核对 Models 的 inject/apply/provide/Effect 模式、NyaCore 公共 API 与依赖撤销语义、核心源码运行时导入、Anybox Web 入口和静态图限制。尚未执行实现或浏览器实验。

根 `npm run check` 已尝试，当前执行环境找不到 npm，命令以 127 退出，未进入构建或测试。Python 静态检查通过：4 个相关 Markdown 文件的 123 个本地链接目标存在，两篇 proposed Note 状态及必备章节齐全，无行尾空白；`git diff --check` 通过。两项定向只读核验提供了组件生命周期与浏览器承载的源码证据；这些结果不代表组件、浏览器兼容或运行行为已经实现与验收。
