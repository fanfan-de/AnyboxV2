# Anybox 产品设计草案

版本：v0.1  
更新日期：2026-10-03<br>
状态：供产品负责人修订的讨论稿

本文定义 Anybox 的产品定位、用户价值、宿主与应用的职责、用户制作应用的主要流程，以及第一阶段的建议范围。它用于先确定产品方向，再指导具体功能设计和技术实现。

**Anybox 的定位草案：一个让用户创建、管理和使用自己应用的工作台。** 应用可以面向不同领域；Agent 是其中一种应用和可选的创作能力。用户制作出来的功能应能成为可以再次打开、保存数据并持续改进的应用。

全文采用三种状态：**已明确**表示用户在本次讨论中明确表达的意图；**建议**表示本稿提出、仍可修改的方案；**待决定**表示尚未作出选择。下文每节标注其状态，建议范围内的具体条目均为提案。目标体验不代表当前已经实现。

修订时建议先看“产品定位”“第一阶段范围”和“需要优先决定的问题”，再补充页面与交互细节。技术现状见“当前实现与目标的距离”；本文不替代现有组件契约和工程验收。

## 产品定位

### 已明确的方向

- Anybox 后续会加入多个领域的功能，其中一些与 Agent 没有强关联。
- 用户应能通过 Anybox 自己制作不同的功能，并直接使用。
- 产品需要处理通用外壳与各应用独立界面之间的关系。
- 产品方向应形成可持续修订的文档，作为后续设计与开发的依据。
- 最左侧窄条承载不同应用的入口；应用切换只使用左侧入口，去掉顶部应用标签栏。
- 除最左侧窄条外，右侧整个区域的布局由应用内部组件呈现，宿主不再提供顶部标题栏和操作栏。

### 建议的定位表述

Anybox 为用户提供一个使用和制作应用的统一入口。用户可以打开已有应用完成具体任务，也可以围绕自己的需求制作应用，在使用中继续修改。

“应用”是用户理解和管理功能的单位。应用可以提供列表、表格、表单、画布、看板或对话等界面，也可以按需使用 AI。用户无需理解 NyaCore、组件装配或运行时等技术概念。

Anybox 的长期价值在于：个人需求能够变成可反复使用的软件，应用及其数据有稳定的归属，用户可以随着需求变化继续改造它。

**待补充：** 对外介绍 Anybox 时最希望强调的价值、第一类要解决的真实问题，以及最终采用的一句话定位。

## 用户与使用情境

本节为**建议与待验证假设**，尚未经过用户研究。使用者与创作者是两种行为角色，同一个人可以同时承担两者。

| 角色 | 想完成的事情 | 产品应提供的帮助 |
| --- | --- | --- |
| 应用使用者 | 找到合适的功能，完成工作，下次继续使用 | 清晰入口、适合任务的界面、可靠的数据保存 |
| 应用创作者 | 把自己的具体需求做成可用功能，并持续修改 | 创建入口、试用反馈、保存和更新应用的完整流程 |
| 进阶创作者 | 更精确地控制应用行为和界面 | 可选的代码或配置编辑能力，具体方式待决定 |

建议优先验证个人用户为自己制作小型应用的情境。团队协作、对外分发和商业化可以在个人使用价值成立后单独设计。

候选场景包括个人物品清单、素材整理、阅读记录、项目数据看板和 Agent 工作区。这些是探索样例，不是首版必须提供的应用目录。

**待补充：** 首批用户是谁，他们现在如何完成任务，最迫切的三个需求是什么，以及他们愿意投入多少学习和维护成本。

## 核心概念

本节为**建议**。

| 概念 | 面向产品的定义 |
| --- | --- |
| Anybox 宿主 | 提供应用入口、工作区和应用管理，承载应用的使用与创作流程 |
| 应用 | 围绕一个相对完整的目的提供功能，具有自己的界面、行为和数据归属 |
| 应用内部功能 | 服务于该应用目的的页面或操作，例如清单中的筛选、导入和统计 |
| 创作草稿 | 尚在修改和试用的应用内容，不立即替换用户正在使用的版本 |
| 可用版本 | 用户明确选择用于日常使用的一份应用版本 |
| 应用数据 | 用户使用应用产生的记录，需与应用代码和创作草稿分别管理 |
| 宿主能力 | 应用按需使用的公共能力，例如保存数据或访问用户指定的文件 |
| Anybox Harness | 当前已有的 Agent 应用；未来可以参与应用创作，产品名已确定；通用服务端核心称为 harness server |

建议以用户目的划分应用：当一个功能有独立的使用理由、适合独立进入，并有相对清晰的数据与生命周期时，才把它设计成独立应用。一个按钮、一项设置或一个页面通常属于已有应用。

首期建议优先承载有界面的小型应用。脚本、自动化流程、后台服务和跨应用插件是否作为其他扩展类型，留待真实场景验证。

## 产品原则

本节为**建议**。

1. **应用围绕具体任务设计。** 不同领域可以采用不同的信息结构和交互方式。
2. **宿主保持清晰而克制。** 用户能辨认自己正在使用哪个应用，能方便地切换、管理和返回；日常操作尽量在应用内完成。
3. **制作的结果能够持续使用。** 生成代码或看到预览只是中间步骤，保存、再次打开和保留数据属于完整体验。
4. **创作与使用可以分开。** 一个应用可以由 Agent 辅助制作，也可以在日常使用时完全不调用模型。应用本身需要 AI 的，应明确说明该依赖。
5. **修改应用时保护已有成果。** 草稿、可用版本和用户数据有清晰边界，失败时能知道保留了什么以及下一步如何处理。
6. **权限与影响能够被理解。** 用户能够知道应用会读取哪些数据、访问哪些资源，以及授权后的作用范围。
7. **通过真实应用确定公共能力。** 新的宿主能力应有明确的应用需求和用户价值，再决定是否抽取为通用功能。

## 宿主与应用的职责

本节的产品责任为**建议**；左侧窄条以外的全部界面归应用内部组件呈现为**已明确**。具体业务责任与公共能力仍可修订。

| 范围 | 主要职责 | 界面归属 |
| --- | --- | --- |
| Anybox 宿主 | 应用入口、切换、创建入口、应用管理、权限与全局偏好 | 最左侧窄条及其管理浮层；右侧只提供挂载容器 |
| 具体应用 | 领域数据、业务规则、任务流程、内部导航与内容呈现 | 窄条右侧的全部布局及自己的设置页面 |
| Anybox Harness | Agent 会话、任务执行及相关配置 | Agent 工作区 |
| 应用创作体验 | 描述需求、修改内容、预览、验证、保存可用版本 | 具体承载位置待决定，可调用 Anybox Harness 能力 |

宿主统一处理应用之间的关系；应用决定自己内部的结构。例如，物品清单可以默认显示表格，素材整理可以默认显示图片网格，Anybox Harness 可以默认显示会话。三者共享外层导航，但不需要共享同一套业务页面。

公共视觉规范建议覆盖可读性、焦点、键盘操作、通用反馈和主题适配。应用可以在这些约定下选择合适的布局。具体视觉规范与主题能力另行补充。

模型、文件、存储等能力是否向其他应用开放，要按场景逐项决定。当前属于 Anybox Harness 的实现，不因产品定位变化就自动变成公共宿主能力。

## 主要页面与信息结构

本节的页面职责为**建议**；左侧应用入口、取消宿主顶部栏和右侧全部界面由应用呈现为**已明确**。其他页面安排仍可修订。

### 已明确的应用导航

最左侧窄条是不同应用的入口，按注册目录顺序显示全部应用，并标记当前应用。应用切换使用左侧入口。窄条右侧的整个区域从顶边开始由当前应用内部组件呈现，应用自行决定标题、项目、会话、页面、设置导航和工作区布局；宿主只提供无装饰的挂载容器。

切换已打开界面保留挂载、草稿、滚动和数据，隐藏的后台界面设为 hidden/inert；切换使用 select，不重复执行 open。左侧导航支持上/下方向键与 Home/End。窄条底部“关闭界面”只关闭前端，显式停止应用独立控制后台，图标按钮通过 title 与 aria-label 说明动作及应用名称。“我的应用”在窄条打开管理浮层，保留当前应用界面；宿主通知、加载状态、界面失败和重新加载入口也放在此处。没有活动界面时右侧留空。现有 sessionStorage 工作区保持 anybox.apps.workspace.v1 和 tabs 字段，以兼容已有位置记录。

| 页面或区域 | 用户在这里完成什么 | 首期建议内容 |
| --- | --- | --- |
| 我的应用 | 找到并打开已有应用，开始制作新应用 | 应用列表、名称与说明、创建入口、管理入口 |
| 应用工作区 | 使用当前应用并在应用间切换 | 当前应用标识、切换入口、应用自己的内容区 |
| 应用创作 | 把需求变成可使用的应用 | 需求描述、修改入口、预览、问题反馈、保存可用版本 |
| 应用管理 | 理解来源、修改应用、处理版本和数据 | 基本信息、当前版本、权限、数据管理和删除入口 |
| 全局设置 | 调整影响整个 Anybox 的偏好 | 仅容纳已实现且确属全局的设置 |

“我的应用”可随时从左侧窄条打开管理浮层。启动时自动打开管理浮层还是恢复上次工作区，需要结合首批用户的使用频率决定。

普通使用界面应使用“打开”“修改”“保存版本”等用户能理解的动作。只有需要排查问题时，才逐步呈现技术诊断信息。

**待补充：** 默认首页、创建入口的位置、创作与使用如何切换，以及首期需要适配的设备与屏幕尺寸。

## 核心使用流程

本节为**建议**。这些流程描述目标体验，不表示现有系统已经支持用户创建应用。

### 使用已有应用

1. 用户在“我的应用”找到目标应用，或者回到上次使用的位置。
2. 打开应用，看到自身界面和已保存的数据。
3. 完成任务；应用明确反馈操作结果和保存状态。
4. 切换到其他应用，稍后回来继续操作。
5. 关闭界面后，再次打开仍能看到已保存的数据。

空列表应解释应用能做什么，并提供第一个有效操作。加载失败应在受影响的应用中显示原因和恢复入口，保留用户仍可使用的其他应用入口。

### 制作一个新应用

1. 用户选择“创建应用”，说明想完成的任务、需要记录的数据和期望的交互。
2. 系统帮助形成第一份可编辑草稿。自然语言、模板、代码编辑的支持顺序待决定。
3. 用户在预览中用样例数据尝试完整任务，提出修改。
4. 系统说明应用所需的能力，以及哪些能力需要用户授权。
5. 用户验证主要流程后，为应用命名并保存为可用版本。
6. 应用出现在“我的应用”中，用户可以进入日常使用。

创建过程中断时，应保留已经保存的草稿。预览失败时，应保留需求和编辑内容，显示可理解的问题反馈。对外分享与公开发布是另一个产品动作，不包含在“保存为可用版本”之中。

### 修改一个正在使用的应用

1. 用户从应用管理进入“修改”，基于当前可用版本建立草稿。
2. 用户调整界面或功能，在预览中验证。
3. 如果修改影响数据结构或增加权限，系统在应用更新前说明影响。
4. 用户确认后，将新版本用于日常使用。
5. 更新未成功时，明确显示当前仍在使用哪个版本，以及下一步的处理方式。

建议第一阶段只支持能够保留既有数据的受限修改。涉及数据结构破坏或不可逆迁移时，先要求明确的备份和迁移设计；应用代码回退不能被当作数据已经恢复。

### 处理失败并继续使用

用户需要区分应用界面加载失败、应用操作失败和创作预览失败。每类反馈应说明本次操作是否完成、输入是否保留、能否重试，以及如何回到可用状态。

对于可能已经产生外部效果的操作，不提供含义不明的自动重复执行。应用应根据自己的任务性质给出后续处理入口。

## 应用生命周期与数据体验

本节为**建议**。

| 用户动作 | 预期体验 |
| --- | --- |
| 切换应用 | 保留合理的界面位置与未提交输入；后台任务行为由应用明确说明 |
| 关闭界面 | 已保存数据保留；存在未保存编辑时提示处理；不默认取消已接受的后台任务 |
| 停止运行 | 适用于确有后台活动的应用，明确说明对任务的影响与停止结果 |
| 修改应用 | 进入创作草稿，日常使用版本有明确标识 |
| 更新应用 | 显示更新结果，保留约定范围内的已有数据 |
| 删除应用 | 说明应用与数据各自会如何处理；删除数据需要明确的用户选择 |

简单应用不必常驻显示“启动”“停止”等控制。只有这些动作能帮助用户管理真实活动时，才出现在常用界面。

建议区分三类内容：应用定义与版本、创作草稿、应用使用数据。首期明确每一类保存在哪里、何时保存、怎样导出或删除。预览默认使用样例或独立测试数据；如果要使用真实数据，应让用户明确选择并理解影响。

运行环境和数据位置是需要单独决定的问题。现有 Anybox Harness 的本地与远程接入不能直接视为所有用户应用都已具备的能力。首期是否限制为单人、单一运行位置，见后文决策表。

## 权限与应用来源

本节为**建议**，约定用户应获得的知情和控制能力，具体隔离机制另行设计。

应用可以来自官方、用户自己制作，或未来的外部导入。界面应展示其来源；来源信息不代替用户授权，也不自动说明代码具备何种可信程度。

建议按照实际用途逐项说明能力，例如“保存本应用的数据”“读取你选择的目录”“连接指定服务”或“使用模型生成内容”。权限请求出现在用途明确的位置，并提供拒绝后会发生什么的说明。

用户应能查看和撤销已授权能力。新增权限需要重新说明，不能随着应用更新静默扩大访问范围。应用数据之间默认具有明确边界，跨应用共享需要单独定义。

自制或导入代码的执行边界，是开放创作入口之前必须解决的实现条件。现有受信应用注册方式不能直接视为任意用户代码的运行环境；NyaCore 的服务名称和依赖注入也不构成权限隔离。

**待补充：** 首期开放哪些能力、授权的粒度与有效期、拒绝和撤销后的应用体验，以及资源使用限制如何呈现。

## 第一阶段范围

本节为**建议**，尚待产品负责人确认。建议先验证一个目标：用户能制作一个与 Agent 无关的小型应用，并在后续使用和修改中持续保留自己的数据。

### 建议的样板应用

使用“个人物品清单”作为验证样例：记录物品名称、分类、位置和备注，支持新增、编辑、删除、搜索和分类筛选。这个样例便于验证数据与界面，不代表产品只面向清单工具。

用户制作出第一个版本后，再提出一次真实修改，例如增加“使用状态”字段。修改完成后，原有记录仍应可用。应用日常使用不需要调用模型，以验证制作过程与使用过程能够分开。

**待补充：** 最终样板应用、真实使用者、样例数据，以及其愿意持续使用的具体理由。

### 建议纳入

- 应用列表、打开与切换，能够与现有 Anybox Harness 共存。
- 一条完整的应用创作路径，具体输入方式先选一种。
- 草稿保存、受控预览和保存为可用版本。
- 一种明确的数据保存方式，覆盖重开和更新后的保留。
- 最小权限范围、可理解的错误反馈和恢复入口。
- 基于现有版本修改应用，并验证数据兼容。

### 建议后续再评估

公开应用市场、付费分发、多人协同编辑、任意后台服务、跨应用工作流、多设备同步，以及复杂应用的通用数据迁移。它们分别需要独立的用户场景和验收，不作为首个创作闭环的前置条件。

### 建议验收标准

- [ ] 目标用户无需手工修改 Anybox 宿主源码，即可走通选定的应用创作路径。
- [ ] 自制应用出现在应用列表中，可以与 Anybox Harness 分别打开和切换。
- [ ] 样板应用能够完成记录的新增、查看、编辑、删除与筛选。
- [ ] 应用关闭、重开以及宿主重启后，已保存记录仍然可用。
- [ ] 用户修改并应用新版本后，既有记录按约定保留。
- [ ] 预览或更新失败时，草稿有保留，当前可用版本和数据状态明确。
- [ ] 应用只获得声明并授权的能力；拒绝权限时有可理解的处理方式。
- [ ] 自制应用失败时，用户仍能使用宿主导航和其他应用。
- [ ] 样板应用保存完成后，日常使用不依赖 Agent 对话或模型调用。
- [ ] 观察真实使用者再次使用和修改应用，记录阻碍与放弃原因。

## 当前实现与目标的距离

本节为**当前实现记录**，依据仓库现有设计与接入文档整理，不构成用户创作能力已经完成的声明。

| 范围 | 当前实现 | 本草案提出的后续目标 |
| --- | --- | --- |
| 应用承载 | 受信应用目录、启停和资源归属；正式目录提供 Anybox Harness | 承载更多领域应用，并形成用户制作应用的接入方式 |
| 浏览器工作区 | 左侧应用入口与工作区路由，应用通过原生 ESM 呈现右侧全部界面；关闭/停止控制和管理浮层归左侧窄条 | 保持应用界面独立，并完善创作与管理入口 |
| 应用加入方式 | 随项目构建，通过受信注册入口加入 | 用户在产品中创建、保存和使用应用 |
| 用户创作 | 尚未提供完整的创建、预览、保存版本和更新闭环 | 验证第一条完整创作路径 |
| 运行权限 | 现有目录用于受信代码 | 为自制或导入代码定义执行与授权边界 |
| 数据与版本 | 现有应用管理各自领域数据 | 明确自制应用的草稿、版本、数据与更新关系 |

实现依据：[通用应用宿主](products-v1.md)、[应用开发者接入](application-development.md)、[宿主与 Anybox Harness 边界](harness-module-boundary.md)。

浏览器外壳是否进一步使用 NyaCore 组件，是服务于产品目标的技术选择；它不单独作为产品里程碑。现有宿主与应用目录分离可以保留，新增架构能力由上述目标体验和验收推动。
