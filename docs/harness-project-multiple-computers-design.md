# Anybox Harness 项目接入多台 Computer

Anybox Harness 0.1.13 接入项目多工作区。一个 harness server 可以同时连接多台 Computer，一个项目可选择其中的多台，供 Agent 在同一会话和 Run 中使用。[当前 Computer 环境](modules/computers/environments.md) · [此前的多目标讨论](agent-execution-environments-design.md)

## 用户看到的项目

一个项目拥有一个**主工作区**和零到多个**附加工作区**。每个工作区都明确属于一台已接入的 Computer，有自己的绝对目录和稳定身份。主工作区决定侧栏文件树、文件引用、默认编辑和测试的位置。附加工作区让同一 Agent 可以访问服务器等其他设备上的资源。

以项目「商店网站」为例，两台机器可以使用不同系统、账号和目录。

| 项目中的名称 | Computer 与工作目录 | 本次任务 |
| --- | --- | --- |
| 开发机 | 开发者的 Mac，`/Users/me/shop` | 修改源码、测试、构建，把经过验证的版本发布到项目已有的制品库 |
| 预发布服务器 | Linux 服务器，`/srv/shop` | 取得指定版本、运行已有发布流程、检查运行版本与日志 |

「本机」始终相对于所选 harness server。若 harness server 运行在第三台机器，开发者的 Mac 和部署服务器均可作为远端 Computer 接入。

### 接入、选择与观察

1. **接入设备。** 用户在当前 harness server 的「执行环境」里生成附着码，在服务器上启动 Computer worker 并完成附着。服务器管理员决定允许该附着访问的目录和工具。多项目可复用同一已批准的附着。[现有接入流程](computer-worker-management.md)
2. **添加到项目。** 点击侧栏项目名称旁的设置按钮，打开「项目工作区」。新建项目时选主工作区。在已有项目里点击「添加工作区」，选择已接入的设备，命名为「预发布服务器」，填写该机的工作目录。目录由目标 worker 按自身文件系统与目录授权核验。附着尚待批准或目录还未通过核验时，界面显示具体原因。
3. **给 Agent 授权。** 项目成员列表表示“可选”。「Agent 工具」决定这个 Agent 在每台设备上能用哪些工具。新加的设备需要有针对该目标的有效授权。新建会话时，用户看到已选的主工作区，可以勾选附加工作区。提交时验证每个选中目标的工具授权。单次会话最多选择 32 个工作区（含主工作区）。只做本地开发时可以只选开发机。
4. **在一次对话中工作。** 输入框旁显示本会话纳入的电脑。工具轨迹逐项显示「开发机 · 运行测试」或「预发布服务器 · 查看日志」，点开可见实际工具名、工作目录、操作状态及回执。两台电脑具有相同路径、同名工具或相同进程编号时，界面仍保留各自的归属。

## 一次发布如何走完

下表是同一 Run 的顺序示例。首版采用现有串行工具调度。具体测试命令、制品库和发布脚本由用户项目提供。

| 顺序 | 执行目标 | 进入下一步需要的事实 |
| --- | --- | --- |
| 1. 修改、测试 | 开发机 | 固定候选源码版本，在对应内容上运行测试，取得退出码和测试结果。测试失败时在开发机修正。服务器端尚无发布动作。 |
| 2. 交付同一版本 | 开发机 → 已配置的发布渠道 | 从经测且未变化的源码构建制品，取得不可变摘要。若测试对象是制品本身，直接发布已测制品。同版本无法证明时重新构建或测试。 |
| 3. 部署 | 预发布服务器 | 先将本次发布请求 ID、目标服务及版本写入操作记录，再让服务器的发布脚本按摘要取件、核验并应用。能支持幂等的发布系统复用该请求 ID。采用源码部署的项目可约定仓库身份和完整 commit SHA，并固定依赖与构建输入。 |
| 4. 核验、读日志 | 预发布服务器 | 查询实际运行的版本或摘要、健康状态及本次发布对应的有界日志。轨迹记录请求的版本、观察到的版本和发布回执，区分“已提交部署”和“服务已运行该版本”。 |

开发机上的未提交补丁不会自动出现在服务器上。Git 路径要求将经过测试的修改纳入确切提交并发布。制品路径可以包含工作区修改，须先固定构建输入，并按产物摘要交付。若开发机是 Mac、服务器是 Linux，需要按服务器的平台与架构构建，并在匹配环境验证可运行性。使用多架构镜像时还要核对服务器实际选择的镜像摘要。服务器取得凭据的方式沿用其部署账户或现有发布服务。模型只需要版本引用和经过筛选的结果。

首版的发布前提是两端有可访问的 Git 仓库、制品库，或能提供同等版本与回执的既有发布系统。对于只有两台 Computer、没有共享渠道的项目，可在后续增加**显式制品传输**。发送端从指定工作区选取一个产物，接收端按摘要、大小和目标目录授权验收，暂存后原子交付。中断后查原传输回执。这是独立的交付能力，现有 worker 的图片字节通道不承担通用文件同步。

发布可以使用服务器上已有的命令工具。示例流程先产生一个稳定发布请求 ID，将它与版本一起作为发布脚本的输入。由 Harness 在工具操作接受时保存这次调用。脚本应让发布系统按该 ID 受理和查询。若需要在界面直接呈现结构化发布状态，项目也可提供返回发布回执的专用工具。任意 shell 命令的退出码只描述该进程，Harness 无法从命令文本推断发布系统的执行状态。

若项目要求“测试通过才允许生产发布”由系统强制，发布端应校验绑定到该版本的 CI 结果或构建证明，并只暴露受限发布入口。通用 shell 的权限由目标操作系统账户决定，用途标签、工作目录和提示词都无法把任意命令限制为部署或只读日志。服务器可以按实际需要提供专用工具，或以受限账户运行既有命令。发布完成后的服务生命周期由部署系统持有，Run 等待自己启动的部署调用及日志读取退出。

## 如何让模型和 worker 选中同一台机器

**一个会话固定一份工具映射，每个模型工具名只通向一个工作区。** 下面的名称仅示意一种会话声明。实际路由用持久身份解析，用户展示名可以独立更改。

| 模型可见的函数名 | 原工具契约 | 固定目标 |
| --- | --- | --- |
| `main__codex_apply_patch` | `codex.apply_patch` | 开发机的项目目录 |
| `main__codex_exec_command` | `codex.exec_command` | 开发机的项目目录 |
| `workspace2__codex_exec_command` | `codex.exec_command` | 预发布服务器的工作目录 |
| `workspace2__codex_write_stdin` | `codex.write_stdin` | 该服务器工作区中已创建的进程 |

- **项目与会话。** 项目保留现有主目录身份，为附加绑定分配独立 ID，记录附着、目标核验过的路径、工作区版本和配置修订。配置写入校验预期修订。同设备同规范目录的重复添加返回已有绑定或明确冲突。会话创建时保存所选绑定及版本，首次成功受理的 Run 固定指令、工具声明与授权映射。新加设备从新会话选择。重命名只改变展示。换机、重绑目录或撤销会切断旧绑定的新准入，历史仍可按当时的名称查看。
- **工具声明。** 每个工作区有稳定且无冲突的工具前缀。同一工作区内沿用原工具的公开函数名或经校验的稳定短名。生成的名称符合四种原生协议共同支持的字符和长度，与 MCP 及其他工具一起校验唯一。新快照按「工作区绑定、确切目标、原 toolId、契约版本」判定工具身份是否重复，单独校验模型别名全局唯一。这样两台机器可以各自声明同一原 toolId。既有快照仍按原规则解码。展示名称、排序和请求参数均不能改变路由。固定表同时保存模型别名、原调用名、原 toolId 及契约版本、项目绑定、确切目标和授权代次。参数校验、依赖检查与 worker 分派使用原契约。已有单机声明沿用已有名称。
- **执行前复核。** 准入取会话选择、项目现行绑定、Agent 授权、工具契约及目标设备上限的交集。每个实际函数分派和模型发送仍复核其所需授权。工作区的 shell 与路径提示分别给出。程序产生的进程句柄带来源，读写 stdin、轮询、取消均须匹配创建它的工作区。Agent 无法用一个工具参数传入任意主机地址或另一个目录来改绑。
- **历史与路由。** 每次 Run 保存本轮解析的确切绑定。接受工具操作时，将稳定的操作 ID、模型实际所用的别名、原工具及工作区身份随调用意图一起持久化。跨 API 续聊保留工具调用和结果的别名配对。复用原生缓存还须核对工具映射与绑定相容。模型切换、设备排序变化、恢复或重命名均不得让旧调用指向另一台机器。[现有工具快照](../packages/execution-environments/src/snapshot.ts) · [Computer 适配](../packages/app-harness/src/core/tool-environments/computer.ts) · [跨协议历史](../packages/app-harness/src/core/protocol-agents/portable-history.ts)

### 接口与数据归属

接口由 Harness 执行端提供，客户端网关继续固定所选实例。沿用现有创建项目接口写入主工作区，项目成员由 `GET /projects/:id/workspaces`、`POST /projects/:id/workspaces` 及成员的 `/rename`、`/remove` 操作管理。执行端路由与客户端网关使用相同的操作边界。

| 入口 | 输入与结果 |
| --- | --- |
| 项目电脑列表 | 按项目返回配置修订、绑定 ID、展示名、主工作区标记、目标目录和验证状态。在线状态取当前 Computer 投影。 |
| 添加、改名或解除项目绑定 | 提交预期配置修订和幂等请求 ID。使用中的附加工作区需要等待 Run 终结才可移除。添加时在目标侧核验目录，再在执行库事务中复核项目修订和附着代次。解除绑定仅退役该项目的关联，不撤销机器与整个 harness server 的附着。 |
| 创建 Session | 可选提交工作区绑定 ID 集合及所见项目修订。服务端总是纳入主工作区。旧客户端省略集合时仅使用原主工作区。服务端验证归属与 Agent 授权。模型调用参数只消费已经固定的映射。 |
| Run 工具轨迹 | 返回每次调用的目标名称、当时的工作区、公开操作状态和经筛选的结果。原始 worker 凭据、恢复句柄与发布账户凭据留在各自资源所有者一侧。 |

## 资源、取消和恢复

通用授权层按目标分别获取、恢复和释放资源。Workspaces 分别固定各工作区的目录身份，Computer Operations 为同一 Run 持有多个设备作用域，worker 按作用域识别附着和进程。[Workspaces](../packages/app-harness/src/core/workspace/component.ts) · [Computer Operations](../packages/app-harness/src/core/computer/operations-component.ts) · [worker 账本](../packages/app-harness/src/core/computer/worker-component.ts) · [按目标授权](../packages/execution-environments/src/run-authority.ts)

为每个实际使用的「Run、项目工作区绑定、确切目标」分配独立、持久的 worker scope ID，父 Run 保存其映射。工作区保留、进程句柄、取消和关闭操作及回执都归该 scope。通用授权继续按确切工具目标核对。首版同一项目只允许同一 Computer 附着加入一次。不同附着仍可能通向同一物理 worker，两个子 scope 也必须独立。worker 能力须经协商，无法安全区分子 scope 的旧版本应在派发前报告需升级。每台机器只在首次需要其资源时取得 scope。

| 情况 | 用户和系统能观察到的结果 |
| --- | --- |
| B 在部署派发前离线 | 已完成的 A 端测试和产物引用可查。B 显示不可用。若未越过发送提交点且能证明未派发，后续可发起新尝试。A 和其他机器均不会接收这条部署。仅选择 A 的会话可照常工作。 |
| B 已收到部署，回执丢失 | 按原 worker 操作 ID 和派发前保存的发布请求 ID 查询。发布系统若只在丢失的响应里返回发布 ID，应显示原操作结果未知并停止自动重发。读到服务运行相同版本是一项独立观察，同版本的并发发布也可能产生该结果。 |
| 用户撤销 B 权限或取消 Run | 撤权立即阻止 B 的新调用。沿用普通会话的固定工具声明，撤权触及已准入的 scope 时取消整轮。后续模型发送也需完整声明的授权有效。整轮取消分别通知所有已使用目标，A 已退出即可释放 A 的占用。B 退出未知则保留其记录并阻止成功结算。只选 A 的独立会话可继续。已提交到发布系统的变更须另行查证或回滚。 |
| harness server 重启 | 使用原 Run 的恢复游标和已保存的设备 scope 映射逐目标认领，原工作区、授权代次和操作 ID 均须匹配。保留既有模型请求结果未知时的中断规则。 |
| 两个 Run 同时发布到 B | 两个 Run 拥有独立操作身份。需要排他发布时，由目标发布系统按服务串行或核对预期旧版本。一个 Run 的健康检查必须核对其请求版本，避免把另一 Run 的结果记为自己成功。 |

## 迁移、实施与验收

1. **项目模型和接入体验。** Projects 保存具名附加绑定、修订和退役记录，Workspaces 按项目绑定管理已核验路径。已有本地或远端项目都从原有设备和路径得到唯一主绑定。项目仍保持原 ID。历史按原快照解码，已有可执行会话继续使用其既有设备和工具声明。将 B 加入项目后，可在新会话中选用。
2. **模型与运行路径。** 在版本化快照中区分模型别名与原工具身份，扩展 Computer 的目录、Run 准备、会话操作登记、worker 协议与作用域恢复。旧 Run 按原 scope、控制 ID、摘要与回执恢复。启用新写入前验证所有执行入口的存储版本门禁和各工作目标的 worker 能力。Anybox 宿主管理职责沿用现有边界，项目配置、会话和部署轨迹归 Harness。
3. **贯穿首版的验收。** 用两个独立 worker、两个互异的工作目录、一个真实的临时制品仓和一个可查询版本的测试服务走完整 Run。程序在 A 改文件并运行测试，在 B 部署同一摘要、读取日志。断言 A 的文件和 B 的文件各自在预期目录、B 记录的版本等于经过测试的版本、两端的轨迹归属正确。注入 A 测试失败、产物摘要不符、B 派发前离线和已部署丢回执，验证错误可区分，未知发布计数不会因恢复增加。
4. **协议、权限与兼容验收。** 用两台机器的相同原 toolId 验证新快照写入、读取和恢复，并覆盖四种原生协议及跨协议续聊中的同名工具、目标撤权、相同数字的跨机进程句柄、双 Run 并发、同一物理 worker 的两个附着、单边退出失败以及重启后的原操作查回。旧本地与旧远端项目及在途 Run 用历史样本验证。本版的端到端验证在同一台 Mac 上使用独立 worker 进程、临时 HTTP 制品仓与测试服务。物理跨机和生产发布渠道需另行实测。[既有协议测试](../tests/native-protocol-agents.test.mjs) · [已有多目标恢复测试](../packages/execution-environments/tests/targets.test.mjs) · [worker 故障测试](../tests/computer-worker-resume.test.mjs)

选择按工作区分配工具名，会使模型声明长度随所选机器和工具数量增长。首版通过显式选择任务需要的工作区和工具来控制。给每种工具增加任意目标参数会改变现有工具 schema 及按名称授权的语义。设置进程级“当前电脑”则无法稳定解释并发调用与恢复。只需发布现成版本的项目仍可直接触发既有 CI/CD。需要同一 Agent 在两台设备上独立执行并查回原调用的项目，适合采用本文方案。
