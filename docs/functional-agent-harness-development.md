# 用函数式思想建模 Agent Harness 的开发

状态：架构方法文档，2026-09-23。基于已完成的 H1，指导后续阶段如何拆解需求和验证行为；不提前冻结 H2 之后的公共类型、存储接口或组件目录。具体阶段与验收见 [Agent Harness 重建计划](./agent-harness-plan.md)，H2 的转换规则见 [Run 状态转换设计](./run-state-machine-design.md)。

## 核心问题

开发 Harness 的每项能力，先回答五个问题：

1. **状态**：现在知道什么？由谁持有，能保存多久？
2. **事实**：刚刚观察到什么？事实是否已经发生，还是仅仅希望它发生？
3. **决策**：给定状态、事实和显式策略，下一状态应是什么？
4. **意图**：为了继续推进，需要请求哪个外部操作？
5. **执行**：谁拥有该操作的资源，怎样取消并确认它实际退出？

其中，决策尽量写成无副作用的函数；模型、工具、存储、时钟、ID 生成和 Nya 生命周期留在明确的副作用边界。函数式思想在这里不是“所有东西都必须是纯函数”，而是让业务规则能脱离资源运行，且让资源所有权可追踪。

```text
外部请求或操作结果
        │
        ▼
   归一化为事实 ──┐
                 ▼
       当前快照 + 事实 + 显式策略
                 │
                 ▼
          纯决策函数
                 │
        新快照 + 事件 + 操作意图
                 │
                 ▼
         状态提供方提交
                 │ 提交成功
                 ▼
       AgentLoop 执行意图
                 │
          结果和退出再次成为事实
```

状态提交与意图执行有先后关系，但两者不是一个事务。特别是外部工具：意图已记录而结果未记录时，进程可能已经执行过副作用。恢复时必须承认这种不确定性。

## 第一维：按所有者和寿命划分状态

| 状态 | 包含什么 | 典型寿命 | 所有者 |
| --- | --- | --- | --- |
| 可选配置 | 当前 system prompt、Agent 的工具授权等 | 多个 Run 之间可变化 | 实际提供该选择的 Agent、Session 或用户配置服务 |
| Session | Agent 关联及已完成的对话轮次 | 多个 Run | 状态提供方 |
| Run 快照 | 本次输入、选定配置、阶段、轨迹、预算、修订号和终态 | 单个 Run，可供查询与恢复 | 状态提供方 |
| 在途资源 | 模型或工具调用的取消句柄、`result`、`done`、等待者 | 一次调用的实际执行期 | AgentLoop 与调用提供方组件 |

这四类信息不应混成一个可变对象。在途资源不能靠序列化 Promise 来恢复；配置的当前值也不能代替历史 Run 实际使用的值。

### 可切换的 system prompt

用户可以切换 system prompt，所以“当前选择”是可变状态。它由 Agent、Session 还是用户配置服务持有，应由产品语义决定；Harness 不应默认为全局唯一。一次 Run 被接受时，应原子读取其有效配置并固定本次使用的 prompt 内容或可恢复的不可变版本。后续切换影响新接受的 Run，不悄悄改变已经接受的 Run。

例如，Run A 使用 prompt 版本 7。用户切换到版本 8 后，Run B 使用版本 8；A 的后续模型步骤仍使用版本 7。Session 的历史可以同时包含两次 Run 的结果。若未来需要“切换立即影响正在运行的 Run”，应将其定义为新的显式命令及取消、重启或迁移规则，不能通过读取可变配置引用意外实现。

目前 H1 的 `AgentDefinition.instructions` 是创建 Harness 时传入的固定值，尚无切换能力；上述规则是后续加入该能力时的建模约束，而非对当前实现的描述。

## 第二维：把决策与执行分开

### 事实只描述已经观察到的事

可用项目自有的判别联合表示事实，例如“接受请求”“请求取消”“模型结果已返回”“模型资源已退出”“工具结果已返回”“工具资源已退出”。`result` 是业务结果，`done` 是实际工作和清理退出，两者不能合并成一个事实。外部模型或工具的第三方类型、错误先在适配器内归一化，再进入领域转换。

“调用工具 X”不是事实，而是操作意图。把愿望误写为事实，会让快照看起来像工具已经执行，无法正确处理取消与异常退出。

### 决策函数只计算数据

以下是概念形状，不是预先冻结的接口：

```ts
type Transition = {
  readonly next: RunSnapshot
  readonly events: readonly RunEvent[]
  readonly intent?: RunIntent
}

function advanceRun(
  snapshot: RunSnapshot,
  fact: RunFact,
  policy: RunPolicy,
): Transition
```

纯决策函数负责阶段转换、工具整批校验、授权、预算、取消优先级和终态选择。时间、ID、有效 prompt 版本、工具目录与校验结果等外界信息，须由调用方以显式参数或已归一化的事实传入。函数不读时钟、不产生随机数、不调用模型、工具或存储，也不持有跨调用的可变服务引用。

并非每条规则都必须挤进 `advanceRun`。输入校验、提示词组装、整批工具请求校验、恢复计划等可以是较小的纯函数，再由转换函数组合使用。纯函数的拆分以清晰的输入、输出和不变量为准，不以函数数量为目标。

### 意图是数据，执行者才持有资源

意图描述下一项允许发起的操作及其稳定标识。Run 服务接受请求并提供控制；AgentLoop 在状态提交成功后解释意图，调用模型或工具服务，持有 `OwnedCall`，等待 `result` 与 `done`，再将观察归一化为事实。调用取消后仍要等待实际退出。组件 `apply` 完成初始化后返回；长期 Run 由 AgentLoop 拥有的异步任务推进，不阻塞组件启动。

Nya 按真实资源和替换边界装配模型、状态、Run 协调及后续工具服务。Agent 定义作为启动时校验的只读配置传给消费者。组件通过 `inject` 声明依赖，并使用本轮 `apply(ctx, config, deps)` 的依赖快照。受信组合根处理外部请求时通过 `context.get()` 获取当前服务，不缓存跨组件重启的服务引用。纯领域函数不需要为了“组件化”而包装为 Nya 服务。

## 一次 Run 如何推进

1. **接受**：状态提供方原子检查 Session、同键去重和活动 Run；同时确定本次有效配置。相同键与相同输入返回已有 Run，不产生第二次调用。
2. **准备调用**：纯决策函数根据已完成的 Session 历史和 Run 轨迹形成输入、检查预算，生成模型调用意图。先提交调用阶段与标识，再发起调用。
3. **观察模型**：模型适配器分别结算业务 `result` 和资源 `done`。两者都被观察后，决策函数选择终态或校验整批工具请求。
4. **执行工具**：整批请求全部有效且获授权后，逐项提交意图并串行执行。上一项的 `result`、`done` 和观察记录结算后，才能启动下一项。
5. **取消或结束**：取消首先关闭后续操作准入，再取消在途调用并等待 `done`。清理失败明确报告失败；成功终态与 Session 新增轮次在同一次状态提交中完成。

Run 的对外状态用于回答调用者；内部阶段用于决定下一项操作。不能从事件文案、Promise 是否存在或对外 `running` 状态猜测内部阶段。取消与调用返回同时到达时，依靠状态修订号和原子提交确定单一顺序；每次启动下一项之前检查已提交的当前状态。

## 用同一方法开发每项新能力

每个开发切片按以下顺序处理，先建立可判断的行为，再接副作用：

| 步骤 | 要产出的东西 | 要回答的问题 |
| --- | --- | --- |
| 1. 写场景与不变量 | 正常、无效、取消、失败、恢复场景 | 什么绝不能发生？ |
| 2. 确定状态与事实 | 最小快照字段和判别联合 | 哪些信息必须记住，哪些已经发生？ |
| 3. 写纯规则 | 校验、转换、组装、恢复计划 | 同样输入是否得到同样决定？ |
| 4. 定义意图与边界 | 本阶段必要的端口及项目自有数据 | 谁执行，谁取消，谁等待退出？ |
| 5. 接入 Nya 组件 | 注入、资源登记和关闭顺序 | 依赖撤销时是否停止准入并清理？ |
| 6. 验证端到端 | 行为测试、`npm run check` | 状态、事件与真实执行是否一致？ |

H2 的第一个纵向切片可以是“模型提出一个有效工具请求 → 工具返回 → 结果回填 → 模型给出最终回答”。随后扩展整批无效零执行、多工具串行、预算和取消竞态。H3 再将同样的状态与决策规则接到排他持有的持久状态提供方，定义异常退出后的 `interrupted` 清算；不自动重放可能已经产生外部副作用的工具。H4 再加入真实模型适配器和交互能力。阶段需要什么契约，就在该阶段定义什么契约。

### 测试从不变量出发

- 相同 Session 和同键同输入至多接受一个 Run；同键不同输入被拒绝。
- 无效或未授权的整批工具请求不执行其中任何一项。
- 已提交取消后不启动下一项；在途调用的 `done` 未结算前 Run 不报告终态。
- 已完成 Run 的有效 prompt 版本、轨迹、事件和终态能解释其行为；配置切换不改写历史。
- Session 成功轮次与 Run 成功终态一起提交；失败和取消不伪造成功轮次。
- 异常恢复保留副作用是否已发生的不确定性，不把未确认的工具调用当作可安全重试。

领域测试用表驱动输入、事实和预期转换；组件行为测试验证提交顺序、取消、提供方撤销、替换和实际资源退出。只有纯函数测试不足以证明资源边界正确，只有端到端测试也难以定位错误的决策规则。

## 判断拆分是否合理

面对一个新需求，若能明确指出“它改变哪类状态、引入什么事实、哪条纯规则产生什么意图、哪个组件拥有执行资源”，拆分通常足够清楚。若必须从 Promise、事件文本或当前配置的可变引用推断 Run 应做什么，说明重要状态或事实没有被显式建模。若纯函数需要直接调用 Nya、模型或存储，说明决策与执行边界需要调整。
