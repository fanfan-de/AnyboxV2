# Anybox 多语言治理与接入方案

状态：宿主与 Claude Agent 的中英文 Web 主流程试点已接入并完成本机检查与隔离浏览器验收，其他范围继续按批次实施。2026-11-12 用户确认先不做 Nya 组件，先以真实试点验证，再根据实际重复提取共享代码。当前未建设共享包或 Nya 适配。方向与验证见[试点实现记录](../.agents/notes/implemented/feature/2026-11-12-host-claude-i18n-pilot.md)；原规划见[试点优先方向](../.agents/notes/proposed/architecture/2026-11-12-i18n-pilot-first.md)，早期讨论见[治理提议](../.agents/notes/proposed/architecture/2026-11-12-i18n-governance.md)与[本阶段未采用的组件候选](../.agents/notes/rejected/architecture/2026-11-12-i18n-nya-component.md)。

## 1. 目标与当前基础

先用宿主与 Claude Agent 两个真实消费者验证中英文呈现、边界与迁移方式，再逐步建立复用和治理机制。首期语言标识采用 `zh-CN` 与 `en`，源文案暂用简体中文；英语不绑定某个国家的货币或时区。共享包、通用生成器和 Nya 适配均不作为试点前置。

当前界面使用原生 DOM、HTML 模板和 ESM，各应用通过 `mount(container, context)` 挂载。宿主和 Claude Agent 已各自接入独立翻译实例与静态资源；Anybox Harness 和原生桌面入口尚未迁移。宿主、Anybox Harness 和 Claude Agent 分别有自己的资源、入口及清理职责，方案沿用这些边界。

| 现状与证据 | 对方案的约束 |
| --- | --- |
| [ApplicationWebContext](../packages/application-api/src/web.ts) 保留原有字段，新增可选 locale 快照/订阅 | 应用只接收呈现偏好，不暴露宿主业务或翻译实例 |
| [宿主 HTML](../packages/host/web/index.html) 初始中文；[宿主界面](../packages/host/src/web/client.ts) 按已保存/系统偏好更新 lang、文本、属性和缓存 | 启动应用前已有有效建议，后续切换只改变呈现 |
| [Harness 入口](../packages/app-harness/src/web/harness-app.ts) 重建时先 dispose；[Claude 入口](../packages/app-claude-agent/src/web/app.ts) 检查草稿并清理观察 | 即时切语言须原位刷新呈现，保留应用挂载和业务状态 |
| [公共请求](../packages/application-api/src/web.ts)、[Harness 错误展示](../packages/app-harness/src/web/client-errors.ts)、[Claude 错误展示](../packages/app-claude-agent/src/web/state.ts) 已使用稳定错误码 | 保留错误码，在消费者界面映射本地化说明 |
| [宿主原生入口](../packages/host/src/desktop/main.ts) 与[旧默认发行原生入口](../packages/distribution/src/entrypoints/desktop-main.ts) 都有菜单、退出或错误弹窗 | 桌面需有主进程可读的偏好，且覆盖两条实际入口 |
| [浏览器资源检查](../scripts/verify-web-assets.mjs) 与[安装资源检查](../packages/host/src/package-management/preparation-static.ts) 要求可证明的静态闭包 | 翻译模块及依赖必须进入各自资源索引与完整产物 |

## 2. 本地化范围与稳定边界

本节是各批次共同遵守的范围原则，首个试点只覆盖第 9 节明确的主流程；不要求一次迁移表中全部入口。

| 内容 | 治理方式 |
| --- | --- |
| 菜单、按钮、表单、空态、加载状态、确认提示、快捷键说明 | 迁入资源；一条完整语义一个词条 |
| `title`、`aria-label`、`aria-description`、`placeholder`、校验和屏幕阅读器状态 | 与可见文案一同迁移和验收 |
| 日期、数字、相对时间、百分比、费用、列表连接 | 使用显式 locale 的 Intl 格式化；货币、单位、精度由业务明确传入 |
| 自有错误码、运行状态、能力不可用原因、产品进度通知 | 保留机器事实，界面映射词条；动态信息只传安全参数 |
| 用户消息、文件、项目/会话自定义名称、模型回答、原始工具/SDK 输出 | 按原文展示；其外围标签可翻译 |
| Prompt、模型收到的工具说明、Session 固定快照、原生协议记录 | 按原有业务版本规则管理；UI 语言不改执行输入或历史 |
| appId、API 路径、服务名、模型/工具 ID、错误码、枚举、JSON 键、签名摘要、文件路径、命令与环境变量 | 保持稳定，不进入翻译资源 |
| CLI、日志、开发文档 | CLI 人类说明后续接入；机器输出和结构化日志保持稳定；首期不承诺整套文档双语 |

产品名称继续遵守[命名规范](naming.md)：Anybox、Anybox Harness、Claude Agent 保持品牌名。`harness server`、Run、Session 等的 UI 叫法在术语表统一，代码和兼容标识不随翻译调整。

语言选择属于当前客户端的呈现偏好。两个用户用不同语言观察同一个远端 Run，应看到相同运行事实；不在 execution 根、Models、Session 或 worker 中新增全局语言状态。模型回答语言如以后需要设置，应另设业务能力和版本规则。

## 3. 分层与技术选择

试点直接采用 **i18next core + Intl**，宿主与 Claude Agent 分别进行局部初始化和界面绑定，没有通用运行框架。i18next 已有实例、语言切换、命名空间、回退和复数机制；使用成熟实现完成真实接入。其实例 API 允许各 owner 独立初始化与切换，命名空间可按功能拆分。[实例 API](https://www.i18next.com/overview/api)、[命名空间](https://www.i18next.com/principles/namespaces)。

| 层 | 负责 | 不承担 |
| --- | --- | --- |
| `@anybox/application-api/web` | 可选的宿主语言偏好快照与订阅契约 | 词条、i18next 类型、偏好写入及持久化 |
| 各 owner 的局部初始化/辅助代码 | 直接调用翻译库和 Intl，持有本界面实例及订阅，先验证真实用法 | 预设共享包、通用运行框架、具名 Nya 服务或来源提供方体系 |
| host | 自身语言选择与偏好、宿主文案、桌面呈现同步，向应用发布偏好 | 应用实际语言决策、具体业务文案与执行语义 |
| app-harness / app-claude-agent | 自己的字典、错误映射、原位更新、应用默认语言 | 另一应用或宿主的内部资源 |
| distribution | 兼容发行的菜单、启动与错误提示接入 | 汇总所有业务翻译 |
| 仓库开发工具 | 试点资源/类型的轻量校验与审阅证据；后续按实际遗漏增强 | 首期通用生成流水线、全仓扫描框架、运行时翻译服务或在线下载 |

试点允许少量相似初始化代码分别存在，先验证语言协商、类型和原位更新，不以消除表面重复为由扩大公共 API。宿主和应用显式声明各自依赖，独立构建和发行；库相关用法留在 owner 的局部接入代码。其他应用可以使用自己的翻译库或不接入多语言；某个翻译库、资源格式或以后可能提取的共享包，不得成为宿主安装、生效或打开应用的条件，也不加入宿主固定共享运行时解析表。

备选的 FormatJS `intl-messageformat` 同样支持浏览器/Node 与 ICU 消息语法，适合采用 ICU 的团队；当前建议本仓库维护的资源统一 i18next 原生 JSON 插值/复数格式，避免并行维护两套语法。[FormatJS 官方说明](https://formatjs.github.io/docs/intl-messageformat/)。不选择自写消息替换器，也暂不引入 React/Vue 适配层、翻译 SaaS、在线翻译或独立语言包。

### 3.1 宿主与应用的职责契约

宿主发布当前用户希望使用的界面语言；应用在自己的能力范围内决定如何呈现。宿主没有“设置应用实际语言”的业务控制权，应用也没有通过语言端口修改宿主或其他应用设置的权力。

| 事项 | 最终负责方 | 协作边界 |
| --- | --- | --- |
| 宿主及原生菜单的语言偏好 | host | 由宿主自己的设置入口修改；应用上下文仅提供读取与订阅 |
| 应用支持哪些语言、实际使用哪种语言及缺词条回退 | 各应用 | 默认在支持时跟随宿主建议；不支持时按自身规则回退，宿主不强制补译或接管 |
| 字典、翻译库、格式化实例、功能文案与错误说明 | 各自 owner | 公共语言契约不提供另一方的字典、翻译器、设置存储或业务服务 |
| DOM 更新与本地监听清理 | 各自 owner | 宿主只更新外壳；应用更新自己的容器并注销自己的订阅；宿主不扫描/改写应用 DOM |
| 包完整性、资源归属、版本生效与应用启停协调 | host | 继续执行既有通用规则，应用自己的业务初始化、取消和实际清理仍归应用 |
| 业务语言选择、Prompt、工具声明与历史 | 各应用 | 与宿主呈现语言端口分离，不通过多语言回调改变执行输入 |

宿主语言端口只包含有界的语言标签、呈现修订号和订阅；不接受词条 key、资源路径、回调命令或设置写入。语言通知与 `MountedApplication` 生命周期正交，不调用 `setActive/canClose/dispose` 或控制 API 来落实语言变化。单个应用回调失败应由该边界捕获并报告，不阻塞其他应用或触发自动重挂载；已开始的业务继续遵循原有生命周期。

词条、术语和审阅门禁是本仓库开发规范，不能变成安装器对所有应用内部技术实现的要求。资源验证只证明通用包结构、闭包和来源，不让宿主理解业务词条含义。未来多语应用介绍也只能通过有界声明式元数据展示，由应用声明可用翻译，宿主不能为取文案执行其业务。

### 3.2 当前强制隔离的事实与限制

上述是受信应用遵守的职责与兼容契约，不能宣称恶意应用已经被权限隔离。当前[浏览器宿主](../packages/host/src/web/client.ts)直接 import 同源 ESM，并向 `mount` 传入同一 document 中的普通容器；应用共享 window、document、同源存储和页面可用的请求能力。`appId`、`domId`、`apiBase`、TypeScript `readonly`、冻结快照以及 localStorage 键名前缀，都不构成应用身份鉴权或应用间沙箱。Web 标准也把同源参与者视为同一信任范围。[HTML 标准的 origin 模型](https://html.spec.whatwg.org/multipage/browsers.html#origin)。

后台的受信应用通过[注册工厂](../packages/application-api/src/node.ts)接收组合根，[Nya 适配器](../packages/application-api/src/nya.ts)在该根安装组件。模块路径和服务命名表达归属；包签名与资源校验证明来源和完整性，不能阻止受信执行代码直接使用进程可用能力。这个限制与既有[应用包信任模型](application-packages-design.md)及[准备运行时边界](modules/package-management/archives.md#签名与信任)一致。

桌面当前[最小宿主窗口](../packages/host/src/desktop/main.ts)和[旧默认发行窗口](../packages/distribution/src/entrypoints/desktop-main.ts)均启用 `sandbox/contextIsolation`、关闭 Node integration，但没有 renderer preload；已有[私有 RPC](../packages/host/src/desktop/rpc.ts)属于主进程与 utility process。本方案的偏好桥是待设计能力。Electron 的 context isolation 隔离 preload 与网页环境，不会自动隔离同一页面内的宿主脚本与应用脚本；同页全局 setter 或桥只能校验窗口/参数时，不能据此声称识别了某个应用调用者。[Electron context isolation 说明](https://www.electronjs.org/docs/latest/tutorial/context-isolation)。

因此，多语言实施要通过公共端口、依赖检查、代码审阅与行为验收落实职责边界，同时明确受信代码的可达范围。若未来要求不受信应用在技术上无法访问宿主或其他应用的 DOM、存储和业务能力，需要单独设计隔离承载、可靠的应用身份与授权消息通道，以及相应的后台进程/操作系统权限约束；本次语言机制不承担也不冒充该保证。

### 3.3 试点后按证据提取共享代码

当前不做 Nya 组件，也不预先创建 `@anybox/i18n`、`/nya`、服务键、来源提供方或额外 Context。现有浏览器通过 mount/dispose 已有清晰的呈现资源所有者；局部实例在该边界内订阅、更新和释放即可。普通业务执行根不因 UI 多语言而增加状态。

先完成宿主与 Claude Agent 的可验收实现，再列出重复代码的具体位置、相同语义、调用差异、测试和变化原因。可能出现的重复包括 locale 规范化、固定格式化选项、缺词条诊断和订阅释放；这些只是观察项，不是预先确定的共享 API。

只有两个真实消费者具有稳定的相同语义，提取后确实减少维护和验证成本，才抽取普通函数或实例工厂。仅仅都调用 `i18next.init`、都用 Intl 或字典里都有“保存”不能作为抽取依据。若差异大于共性或封装只转发一层，继续保留局部实现。共享资源不得包含业务字典，也不要求其他应用改用相同翻译库。

提取时再确定放置位置、导出类型、依赖及是否值得新建 workspace 包；不预设包名、提供方目录或通用消息协议。试点验收不以“产出共享包”为成功条件。提取前后需对照双语流程、回退和清理行为，证明复用没有破坏独立发行与应用自治。

本轮试点后的比较结论是保留局部实现：宿主负责持久偏好和跨窗口事件，Claude Agent 负责自己的节点绑定和视图清理，行为不同；当前相似处主要是少量库初始化、局部词条参数类型和 vendor 构建包装。尚不足以证明新增公共运行接口和包依赖可以降低总维护成本，后续扩展应用时再依据新重复评估。

组件候选本阶段不采用，原因及原方案保存在[独立记录](../.agents/notes/rejected/architecture/2026-11-12-i18n-nya-component.md)。若未来出现已运行在 Nya 中的实际消费者，且需要独立替换、撤销和统一清理，再另立需求评估；不能把这件事自动排入后续迭代。尤其需要证明来源失效是否应影响消费者，不能让偏好失效扩大为整个界面退出。

## 4. 语言偏好、回退与兼容

偏好值为 `system | zh-CN | en`，其中 `system` 是偏好，不是翻译资源名。解析结果使用规范 BCP 47 标签；显式选择优先于系统探测。`system` 按桌面系统语言或浏览器 `navigator.languages` 的顺序匹配；英语地区变体匹配 `en`，简体中文与兼容别名通过显式规则匹配 `zh-CN`，未知语言回退到源语言 `zh-CN`。繁体中文不通过自动简繁转换声明支持。

每个应用独立解析宿主建议，并决定实际资源语言与回退。本仓库两个应用建议采用“期望语言 → 本应用源语言”；单词条缺失也只回退本应用源语言，不跨到宿主或另一应用查同名 key。源词条仍缺失时，开发与 CI 报错；生产由资源所属方使用固定的本地化通用提示并记录有界诊断，不把内部 key 当作普通用户文案。卸载、授权等关键动作若连源文案也缺失，由负责该动作的 owner 禁用它并提示界面资源异常，不用通用标签替代确认语义。正式承诺支持的语言应通过完整性门禁，回退不能替代翻译完成。[i18next 回退机制](https://www.i18next.com/principles/fallback)。

源语言与默认回退 `zh-CN` 是为了与现有界面兼容的建议；首批中英文资源均应完整。以后若调整默认策略，应单独记录，不改已有用户显式偏好。

| 场景 | 偏好的唯一持有方与同步 |
| --- | --- |
| 普通浏览器 | 当前 origin 的 localStorage，例如 `anybox.preferences.locale.v1`；同页主动通知，其他窗口通过 storage 事件更新；写入失败保留会话内选择 |
| Electron（后续原生入口目标） | 主进程持有 userData 下独立的非秘密呈现偏好，并串行写入；渲染页面经窄桥读取/提交及订阅，主进程同步更新菜单和后续弹窗；不作为浏览器试点前置 |
| 不提供 locale 的旧宿主、测试容器或独立嵌入入口 | 应用以自带的解析规则或入口显式注入构造端口；不要求依赖 host 实现 |

桌面中的 localStorage 不再作为另一份权威设置。若迁入旧浏览器偏好，只在主进程未保存选择且入口明确时做一次性导入；不从活动网页任意读取配置。桌面桥只接受固定偏好值，沿用现有受信页面/IPC 边界。浏览器不同 origin 和不同设备之间首期不做账号同步。

已接入的可选公共契约如下：

```ts
interface ApplicationLocaleContext {
  current(): Readonly<{ preferredLocale: string; revision: number }>
  subscribe(listener: () => void): () => void
}
// ApplicationWebContext 新增可选 readonly locale?: ApplicationLocaleContext
```

`preferredLocale` 表示宿主建议，实际语言是应用内部状态，不由端口设置。快照只包含不可变基础数据，不暴露设置存储引用。应用通过该契约只读取与订阅，不修改全局偏好，不接收宿主的 `t()` 或 i18next 实例；宿主设置写入方法也不加入此端口或通用全局对象。该设计限制公共 API 的能力，现行同源模式仍须遵守第 3.2 节的信任限制。新应用遇到旧宿主按自带默认值运行；新宿主遇到旧应用允许它保持原语言，不把能挂载等同于已完成翻译。缺少语言端口或不支持宿主建议语言，不视为包损坏，不因此阻止安装、生效或打开应用。新增 API 按项目兼容和版本规则发布；旧宿主缺失端口有明确测试。

偏好读取或订阅失败时，界面保留最后已接受语言，首次失败则使用自己的默认语言；报告有界诊断但继续可用，不停止应用或重启页面。各浏览器的实例和语言状态独立，两个语言不同的客户端观察同一 Run 时不得相互覆盖。

宿主维护 `<html lang>`；应用容器按自己实际资源语言标注 `lang`，未来 RTL 的 `dir` 由实际语言确定。时区默认采用查看者设备的时区；需要展示执行设备时间时显式标注。切语言不改存储时间、UTC/ISO 字符串、数值、货币、文件路径和机器排序。

## 5. 资源、词条与翻译质量

本节编辑格式和审阅规则适用于本仓库维护的宿主与应用，不扩展为第三方应用的内部实现或安装契约。

建议资源放在各 owner 的 `src/i18n/locales/{zh-CN,en}/`，按真实功能拆分，例如宿主的 `applications`、`packages`，Claude 的 `workspace`、`permissions`、`account`，Harness 的 `workspace`、`models`、`prompts`、`connections`。目录在实际迁移该功能时创建，不先建空树。

使用稳定语义 key，例如 `packages.install.confirm`、`permissions.request.allowOnce`；同一英文单词在不同语境可分别建 key。禁止用整句中文作 key、业务数据拼 key，或在同一资源里混用自然语言键与语义键。动态状态采用穷举的枚举 → key 映射。共享“保存”“取消”等资源只在各自 owner 内复用；跨应用一致性通过术语表与审阅保证，不要求应用运行时依赖宿主 common 字典。

试点采用能接入现有构建的局部静态资源，可使用带类型的 TypeScript 资源模块；不预设 JSON → ESM、通用参数类型生成或审阅元数据流水线。每个 owner 独立约束 key 和参数类型，利用翻译库已有类型能力与少量局部声明验证不存在的 key、漏传参数和复数分支，不以 `as any` 或任意 `string` 绕过检查。若实际选择 JSON，需补足它无法直接推导的参数类型，而不是默认引入通用生成器。格式与类型做法在两个试点消费者中验证后再决定是否统一提取。[官方 TypeScript 指引](https://www.i18next.com/overview/typescript)。

示例：源语言使用 `selection.count_other: "已选择 {{count}} 个应用"`；英语分别提供 `selection.count_one: "{{count}} app selected"` 与 `selection.count_other: "{{count}} apps selected"`。业务调用语义键并传数字 `count`，不拼接“数量 + 单位”。不同语言允许不同复数分支，校验语义键、参数与该语言要求的分支，不强制原始后缀集合完全相同。[复数规则](https://www.i18next.com/translation-function/plurals)。

日期、相对时间、百分比、费用通过显式 locale 的 Intl 工厂处理；金额保留业务货币（例如 USD）及业务精度，不因语言变化换算或更换币种。展示名称的排序可使用当前 locale 的 Collator；身份、摘要、包校验、恢复计划和持久排序不得改为随 UI 语言变化。[Intl 格式化](https://www.i18next.com/translation-function/formatting)。

翻译值默认只允许纯文本。DOM 写入优先使用 `textContent`、安全属性 setter 或固定节点结构。现有 `innerHTML` 模板不直接插入译文和动态变量；优先先建静态结构再绑定文字。确需模板插入时，只允许显式、经过 HTML/属性上下文验证的转义路径；不能先在翻译器转义又对输出重复转义。i18next 默认转义插值，项目若为安全 DOM setter 提供未转义纯文本适配，必须与模板路径分开，禁止全局关闭后任意拼 HTML。[插值与转义](https://www.i18next.com/translation-function/interpolation)。

试点先维护一份简短术语表与翻译上下文，源文案含义或参数变化时，在同一变更中人工复核对应英语，不只检查 key 存在。流程为开发者提交源文案及上下文 → 人工或 Agent 生成译稿 → 熟悉功能的审阅者确认术语、动作含义和长度。Agent 生成不能自动视为审阅通过。源修订摘要、`needs-review` 状态和自动翻译管理以后按实际遗漏与审阅成本评估，不作为首期前置系统。

## 6. 原位切换与生命周期

切换过程是更新呈现快照、各 owner 的翻译/格式化实例及现有标签，不执行 reload、remount、业务 open/close 或请求重放。保留输入值、附件草稿、IME 输入、选区、焦点、滚动、展开状态、权限弹窗及 Run 观察。隐藏但仍挂载的应用也订阅更新；后挂载应用读取最新快照。

静态模板可标记固定的文本/属性绑定，动态界面用显式刷新函数；绑定只更新自有文本和属性，不覆盖输入值或重建整棵工作区。语言端口应在异步初始化前订阅并读取，`dispose` 注销监听、清理绑定和自有定时器；已排队回调须检查当前代及取消信号。

缓存必须纳入 locale/revision，例如[宿主列表缓存](../packages/host/src/web/client.ts)、[Claude transcript frame](../packages/app-claude-agent/src/web/view.ts)。只刷新产品标签，不因 locale 更新重算或改写模型原文。模块顶层的已翻译常量改为 key 映射或调用期计算。内存中的产品提示保留 key/安全参数，确保切换后可以重绘；用户内容仍保留原文。

语言切换原则上不新增退出或取消流程。若尚未迁移的页面无法安全原位更新，该页面明确保留原语言；不得通过默认丢弃草稿或忽略 canClose 来完成语言切换。验收应观察网络和生命周期，证明切换未额外启动/关闭应用或重发 mutation。

## 7. 错误、历史、应用元数据与 CLI

试点先迁入主流程实际使用的 `messageFor` 等错误映射，其余包管理和详细设置错误随对应功能批次接入，保持 HTTP `{error:{code}}` 不变。无需给普通业务 API 加 `Accept-Language`，也不需让后台根持有客户端语言。未知错误显示本地化的通用说明和已有安全诊断码；翻译参数不得加入 token、认证头、原生 continuation 或其他秘密。

Claude Agent 当前既有产品自造 notice，也有 SDK/工具原始 `message`，且[Store](../packages/app-claude-agent/src/core/store/component.ts) 会保存错误 JSON。后续按来源将新产品投影表达为稳定 code 与白名单参数，旧 `{code,message}` 记录保持兼容读取；不能仅凭 code 命中就丢弃有用的原始诊断。SDK/工具原文保留为明确的原始详情，不批量翻译历史或升级旧数据库内容。新增持久字段与事件格式另行设计版本及旧样本测试。

[ProductDefinition](../packages/application-api/src/index.ts) 和[安装清单](../packages/host/src/package-management/archive-types.ts) 目前只有单一名称等元数据；[清单校验](../packages/host/src/package-management/archive.ts) 严格限制字段。首期保持品牌名，应用提供的说明按原文兼容展示，列为元数据翻译缺口，不宣称整个应用目录已双语。未来需要多语应用介绍时，单独设计有界、可静态验证的元数据及包格式兼容；不为读取介绍执行浏览器入口或启动应用，也不直接给现行 manifest 增加 `locales` 字段。

CLI 后续只迁移帮助、交互提示和明确的人类显示模式。若新增 `--locale`，建议优先级为显式参数 → `ANYBOX_LOCALE` → `LC_ALL/LC_MESSAGES/LANG` → 入口原有默认语言；`C/POSIX` 对应英语。它只控制该命令的人类呈现，不改子工具环境的 LANG/LC_*。既有 JSON 的 key、code、枚举、数字、时间、退出码，以及兼容的诊断 message 保持稳定，机器模式不随终端语言改变。日志保留结构化事件和稳定诊断；用户诊断摘要由 UI 翻译。

## 8. 构建、发布与治理门禁

试点由宿主和 Claude Agent 各自静态包含中英文资源，将 i18next 及局部接入代码打入自有浏览器资源，不要求宿主提供新的运行时 import map，也不预先新增 workspace 共享包。已有[Claude vendor 构建](../packages/app-claude-agent/scripts/build-web-vendors.mjs)可参考。验证最小宿主和独立应用的资源及生产依赖闭包，不借源码 workspace 隐式解析。若试点后确需新包，再同步[构建顺序](../scripts/build-workspaces.mjs)、产物依赖和许可证，不把该工作提前成试点门槛。

所有产出进入 owner 的 assets 表、资源索引、payload、摘要闭包与许可证清单；新应用版本按已有包规则发布和生效。保持本地目录为应用包本体，ZIP 仍仅为可选分发形式。翻译文件不能从 CDN、可变源码目录或安装外路径读取。首期不用 `import(\`./locales/${locale}.js\`)`；以后按语言拆分时先设计显式字面量模块表并纳入资源图校验，不放宽现行校验器。

治理随真实试点逐步补齐。首期只增加能发现试点实际错误的轻量检查，不以三个独立命令或一套通用扫描框架为前置。本轮没有创建检查脚本：

| 检查 | 应检查什么 | 门禁策略 |
| --- | --- | --- |
| 试点资源与类型检查 | 双语语义键、必需参数、复数分支、纯文本约束；若使用 JSON 再检查重复键 | 已迁移功能通过局部类型检查和必要的资源校验，不要求生成器 |
| 文案清点与审阅 | 试点 HTML/DOM 文本及属性、格式化、源义变更对应英语；记录尚未迁移的范围 | 按功能检查清单和代码审阅，不把注释/协议样本误当 UI |
| 应用包与资源检查 | 两种语言、运行依赖及许可证均在确切版本闭包内 | 复用现有构建与安装检查，并加翻译资源缺失用例 |
| 双语言行为与界面验证 | 同一用户流程、热切换、草稿/运行不受影响、长文本与无障碍属性 | 每个迁移批次的交付条件 |

试点后若反复出现漏迁、参数或资源失配，再决定是否建设 `i18n:check`、类型生成或 AST/HTML 扫描，并按真实资源格式和 UI 写入位置设计。扫描不能只搜汉字，英文也可能硬编码，中文也可能是注释；届时再评估增量基线与例外记录，避免整文件长期豁免。动态 DOM 行为和翻译质量仍由行为验证与审阅补足。

未使用 key 先报告，检查动态映射、模板及兼容路径后删除。例外记录责任归属与理由，不能用宽泛忽略项掩盖缺失。新增界面要求中文、英文、参数定义、术语审阅及必要界面验证同批提交，并维护对应 Agent Note。
