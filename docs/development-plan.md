# 开发计划

状态：待执行的计划，2026-09-06。旧 harness 已删除，Runtime 从零制作；当前仅保留通用 Nya 应用基础。目标架构见 [architecture.md](architecture.md)，客户端契约见 [runtime-protocol.md](runtime-protocol.md)，共享能力见 [Client SDK 设计](client-sdk.md)。未来组件和客户端尚未实现。

[Runtime v1 制作计划](runtime-implementation-plan.md)是本计划的内核实施细案：9 组 48 类组件，R0—R2 对应 P1 的内核工作，R3—R5 推进 P2 内核能力。本文继续负责 P0—P4 产品路线；内核完成不替代 Gateway、SDK、两个宿主及客户端的验收。

## 1. 开发顺序

首先完成**同一个 SDK 操作本地和独立服务端 Runtime，任务可以补读和显式取消**的最小闭环。它验证产品的公共基础，然后才扩展 Agent 能力和各端 UI。

| 阶段 | 交付结果 | 完成标志 |
| --- | --- | --- |
| P0 现有基础 | Nya 六包装配、JSON 配置控制、启动/关闭、开发 HMR | 已有代码与行为测试；空配置 demo 可启动关闭 |
| P1 Runtime 闭环 | 协议、SDK、持久会话/Run、模拟流、本地与服务端宿主 | 同一客户端测试分别连接两个宿主，完成开始/补读/取消 |
| P2 完整 Agent 能力 | 一个真实模型适配器、两种 BYOK 后端、工具循环、工作区与审批 | 本地和服务端使用相同 Profile/工具契约，权限与取消生效 |
| P3 四类客户端与自部署 | TUI、Desktop、VS Code 扩展、手机 Web/PWA，单用户云端发布包 | 编辑器/电脑开始云任务，手机接续查看与审批；客户端关闭不杀任务 |
| P4 开放扩展与后续规模 | 第三方扩展样例、协议兼容套件；按需求增加托管多用户 | 外部客户端和替代适配器无需修改 Runtime 核心 |

顺序表达依赖，不承诺工期。P1 先做可运行的纵向功能，不要求一次性实现完整协议表中的所有方法。

## 2. P1：最小 Runtime 闭环

### P1.1 定义产品契约

- [ ] 创建 `packages/protocol`：Run 状态、消息内容块、事件、结构化错误、版本和运行时校验。
- [ ] 确定握手、工作区读取、会话 create/list/get、Run start/get/cancel/events 的第一批请求/响应。
- [ ] 为浏览器可用的包配置独立 TypeScript 选项，验证不包含 Nya/Node 依赖。

验收：不导入 Runtime 也能验证请求和解析消息；畸形、越界和未知可选字段具有明确行为。

### P1.2 从零实现 Runtime 内核

- [ ] 创建 `packages/runtime` 和 `runtime/spi` 公共入口，把业务运行与宿主装配分开。
- [ ] 用 Storage 接口实现一次 Run 接受事务，包括消息、Run、事件、Session 版本与幂等记录。
- [ ] 保存预配置 Agent Profile 的固定 revision，首次接受即冻结快照；完整配置编辑与发现能力在 P2 增加。
- [ ] 第一版配套一个本机及单实例服务端都能使用的持久化适配器；内存实现只用于测试。
- [ ] 新建 Sessions、Runs、Agent 实例和模拟流适配器，按新 SPI 实现第一条完整执行路径。
- [ ] 为每次 Run 实现显式取消、等待完成和 Effect 资源登记，确保普通 Run 失败不使应用退出。

验收：接受记录重读后包含同一个 Run；同键重复提交不会再次执行；同会话并发提交只有一个新 Run 被接受；不同会话可并行并受上限控制。

### P1.3 实现 Gateway 和 Client SDK

- [ ] 创建 `packages/gateway`，实现 HTTP 命令及基于持久事件的 SSE 补读。
- [ ] 创建 `packages/client`，实现认证传输、请求键复用、错误映射、事件去重/投影和重连。
- [ ] 按 SDK 设计区分低层事件与 `observeRun` 视图，定义 Client/视图的独立释放；Run 业务状态与连接状态分开。
- [ ] 实现提交准备、结果未知错误和 `PendingCommandStore` 端口；首版服务端保留幂等映射，客户端不在中止提交后自动重试。
- [ ] 将缓存和订阅绑定 Runtime、认证分区和工作区，验证实例重启、账号切换和迟到响应不会串数据。
- [ ] 为所有操作建立受信主体和工作区检查；初始自部署宿主可只有一个用户，测试应包含越权主体。
- [ ] 实现缓冲上限、游标过期后快照恢复，以及接收慢客户端的处理。

验收：断开订阅后任务继续；同一 SDK 重连不缺失或重复显示输出；丢失接受响应后重试不产生第二个任务；其他工作区不能读取或取消它。

### P1.4 落地两个宿主

- [ ] 增加 `apps/runtime-local`，负责当前用户后台进程、数据目录、发现、启动锁和显式关闭。
- [ ] 增加 `apps/runtime-server`，负责网络绑定、认证适配器、就绪状态和服务器生命周期。
- [ ] 两个宿主使用同一个 Runtime 组合入口，差异仅由配置与适配器决定。
- [ ] 增加一个薄命令行客户端用于端到端验收，暂不实现完整 TUI。
- [ ] 保留 JSON/Include 默认装配，内嵌宿主可以直接注入实现；开发 HMR 由宿主显式开启。

验收：在两个独立进程上运行同一套 SDK 合约测试；关闭客户端不停止本地后台任务；显式停止 Runtime 后没有受管任务继续运行，重复关闭结果一致。

P1 必须使用真实持久化和真实进程边界，模型可以是模拟实现。接受 Run 后业务执行独立于 HTTP 连接；先持久提交接受记录，再返回 runId，由客户端补读事件。

## 3. P2：BYOK 与 Agent 执行能力

- [ ] 选择并实现一个真实模型适配器，支持增量输出、工具描述/调用转换、取消及实际可获得的用量。
- [ ] 在 Runtime 内实现 AgentLoop、Turn、Step 的多步模型与工具循环；限制步数、执行期限、上下文大小和工具结果大小。
- [ ] 在 P1 固定 revision/运行快照基础上实现完整 Profile 编辑、发现和能力选择，后续编辑不修改已经接受的 Run。
- [ ] 增加模型注册表、工具注册表的获取/注销机制；注销期间先阻止新调用，再取消并等待受影响任务。
- [ ] 实现本地系统凭据后端和服务端受保护的凭据后端，API Key 与 Runtime 登录凭证独立。
- [ ] 实现 Workspace 接口，先支持受控目录内的文件工具，再加入受管命令执行器。
- [ ] 实现工具授权、待审批记录和跨客户端审批；输入文件和输出产物使用工作区资源引用。
- [ ] 保存工具调用开始/结果；崩溃恢复保留不确定状态，不自动重放外部副作用。

验收：同一 Agent Profile 分别在本地/服务端运行，模型请求由所选 Runtime 发起；密钥不会出现在读取 API、持久消息、事件和受测日志中；未授权工具不执行；取消会结束受管模型流和工具执行并等待清理。

关键竞态测试包括：审批与取消同时发生、模型完成与取消同时发生、组件注销时仍有任务、凭据撤销后的下一次调用，以及工具结束后进程在结果写入前崩溃。

自动测试使用模拟提供商与可控工具；真实模型验证使用专门的开发配置和明确授权的凭据，避免测试默认消耗 API 额度。

## 4. P3：四类客户端与单用户云端交付

先用 TUI 验证交互，再开发 Desktop 与 VS Code 扩展的系统/编辑器集成，随后落地手机 Web/PWA 的前后台与小屏体验。四类客户端共用 SDK，不复制 Agent 调度或协议归并逻辑；VS Code 内部消息桥只适配编辑器宿主。

| 客户端 | 首版功能 | 独有职责 |
| --- | --- | --- |
| TUI | Runtime 切换、会话列表、发送、流式输出、工具进度、审批、取消 | 键盘交互、终端恢复、日志输出隔离 |
| Desktop | 同样的会话能力、设置、工作区和产物浏览 | 本地 Runtime 启停、目录选择、系统凭据与原生桥接 |
| VS Code 扩展 | 会话侧栏、选区/文档上下文、流式进度、审批、取消、差异查看 | 编辑器 URI 映射、文档基线校验、受限消息桥、远程工作区连接 |
| 手机 Web/PWA | 云端会话、进度、审批、取消、产物访问 | 小屏布局、前后台切换、连接恢复；原生推送后续独立增加 |

客户端始终显示当前 Runtime 和工作区；模型配置页将凭据明确保存到选定 Runtime。模型 Key 不作为普通消息发送，也不保存在会话缓存中。

VS Code 子任务：

- [ ] 增加 `apps/vscode`，分开 Extension Host、Webview 和内部消息桥的入口/构建；仅在扩展部分依赖 VS Code API。
- [ ] 在扩展宿主中复用 Client SDK，接入独立 Runtime 发现/启动及用户显式选择的云端连接；Agent 循环不放进扩展进程。
- [ ] 实现侧栏、命令、选区/文档快照、工作区 URI 映射和差异预览；写入前检查当前文档基线及工作区授权。
- [ ] Runtime 登录凭据使用扩展秘密存储；模型 Key 通过专用写入流程保存到选定 Runtime，Webview 不持有长期凭据。
- [ ] 分别验收普通桌面、Remote SSH、Dev Containers，明确宿主类型与实际执行位置；纯浏览器扩展入口后续单独验收。
- [ ] 生成可安装的 VSIX 并验证激活、停用、窗口重载、升级重连；独立 Runtime 的分发与版本检查不依赖 VS Code 内置 Node 满足 Nya 要求。

云端交付包括：可独立安装的包/镜像、挂载数据目录、认证/TLS 配置样例、数据库迁移、备份恢复和宿主退出策略。检查依赖和构建产物不再要求旁边存在 `../NyaCore`；六个框架包使用同批固定版本交付物并完成独立安装验证。

验收场景：

1. Desktop 连接云 Runtime 开始任务，关闭窗口；手机重新认证后读取同一 Run 的输出并完成审批。
2. 手机切入后台导致流断开，恢复前台后用快照/游标恢复，不重复提交任务。
3. TUI 和 Desktop 同时连接本地 Runtime；一方取消，另一方观察到相同终态。
4. 本地模式使用本地凭据和目录；云端模式使用云端凭据和目录；切换连接不会自动迁移或重放旧任务。
5. 服务器重启后，已完成历史可读，未完成任务显示 interrupted；不把“仍有记录”误报为“仍在执行”。
6. VS Code 开始云任务后重载窗口，Desktop/手机仍可观察并审批；扩展恢复后以快照/游标补读，不重新提交该 Run。
7. 扩展停用、Webview 关闭或一个视图断线时，另一个客户端或视图仍能操作共享 Runtime；没有隐式停止 Runtime 的行为。
8. 在 Remote SSH 和 Dev Containers 中验证执行位置、凭据归属和多根工作区映射；同名本地/远程目录不串用。执行容器停止后任务按 interrupted 处理。
9. 未保存的文档内容按明确的版本快照发送；生成差异后用户继续编辑，接受过期差异时报告冲突并保留当前内容。云 Runtime 不因收到文件 URI 就能读取编辑器文件。

在这一步完成前，不把多用户共用可执行任意命令的工作进程作为公开托管产品发布。

## 5. P4：验证开放性，再按需求扩大部署

- [ ] 提供第三方模型和工具扩展样例，分别演示配置、能力发现、卸载取消和资源清理。
- [ ] 用替代存储适配器运行同一套存储/Runtime 合约测试。
- [ ] 提供协议说明和独立客户端示例，不要求加载 Nya。
- [ ] 稳定扩展配置 schema、版本兼容规则以及受信插件安装的管理入口。
- [ ] 若提供托管多用户服务，再增加账号、隔离工作区 worker、配额和管理服务；先验收身份与执行隔离。
- [ ] 若实际规模需要，再增加跨进程队列、任务租约、worker 版本约束和可验证的恢复机制。

本地/云端会话迁移、文件同步、设备桥接、原生手机应用、定时自动化、多 Agent 协作都可作为独立能力加入，不阻塞前三阶段。

## 6. 保留基础与新增模块

| 位置 | 制作动作 | 约束 |
| --- | --- | --- |
| `packages/runtime`（新增） | 从领域契约、Storage、SessionLog 开始，逐批实现 48 类组件 | 模型 SPI、执行循环与 Run 生命周期从零制作；取消后等待真实任务结束 |
| `packages/application/src/index.ts` | 保留通用 Nya 装配；后续将 Runtime 作为同树组件接入 | 空配置可启动、启动失败清理、幂等关闭、每次请求读取当前服务 |
| `packages/application/src/types.ts` | 保持宿主配置/生命周期入口；新 Runtime 业务 API 独立定义 | 无旧 run/model/agent 兼容接口；Context 仅用于受信宿主/扩展 |
| Include 配置 API | 保留在宿主管理入口，选择磁盘配置时由 Include 独占文件声明 | 预览、保存冲突、saved 与运行 partial 分开判断 |
| HMR 控制 | 保留在显式开发装配；新 Run 组件变化增加受影响任务测试 | 不自动重放用户请求；restart-required 交给宿主 |
| `examples/host.mjs` | 保留教学示例；提取其信号/期限经验到产品宿主 | 库内无进程信号和强制退出；产品后台进程不随 UI EOF 关闭 |
| `examples/demo.mjs` | 保留空配置启动/关闭示例；另增有限、无网络 Runtime 示例 | 框架基础与新增 Runtime 都能分别验证，不要求配置真实 Key |
| 根 `package.json` / tsconfig | 按新依赖顺序加入 workspace、构建和检查；区分 Node 与浏览器配置 | TypeScript strict；不引入两份 Core 或源码深层导入 |

旧 harness 代码、模型注入、Agent 就绪检查和 application.run 已移除。后续直接按新契约实现 Runtime，不保留旧接口包装；组件装配、配置/HMR 和宿主生命周期继续复用现有 application。

## 7. 验证策略与开发约定

| 层级 | 重点行为 |
| --- | --- |
| Runtime 执行组件 | 流式循环、工具结果处理、限制、取消、清理等待 |
| Runtime / Store | 原子接受、状态竞争、幂等、工作区边界、崩溃后状态 |
| Gateway / SDK | 进程边界、认证、重复/缺失事件、游标补读、取消订阅不取消任务 |
| 宿主 | 初始化失败、运行关闭、进程信号、后台独立寿命、退出期限 |
| 客户端 | 同一协议下展示一致、审批防重复、切换连接、前后台恢复；VS Code 视图重建、远程工作区映射和文档冲突 |

现有测试覆盖框架装配、配置、HMR 和生命周期，是保留基础的回归基线。新增 Runtime 测试围绕行为与真实边界，不为每个转发函数重复写一套断言。

完成变更运行 `npm run check`；修改示例后运行 `npm run demo`。修改 NyaCore 时在相邻仓库实施，先停止 `nya:watch`，等待 `npm run nya:build` 成功后再验证 AnyboxV2。框架公开入口、Effect 资源归属与 strict 类型约束继续适用。

实现下一阶段时先更新相应契约及验收项，再修改源码，并把实际完成状态同步回本文；不要让设计文档中的目标 API 与 README 的可用 API 混淆。
