# Anybox Harness application package

`@anybox/app-harness` owns the Anybox Harness client, harness server, independent Computer worker and browser resources. The application ID stays `agent`; the original package split preserves server API routes, service keys, database paths and state. Client connections now belong to each application, with private tables and credential namespaces and read-only import of former shared records.

D1.2 adds `anybox.app.json` as the archive recipe and public `package/client` / `package/execution` preparation factories. These factories construct existing registrations without creating a Context or opening business resources; normal initialization remains owned by the later application runtime. The artifact builder supplies the complete production/native closure, static asset index, licenses and external-key content signature. Hosted preparation binds shared Nya/API/SQL imports to the host; separate application processes retain the private offline closure. See [archive contracts](../../docs/modules/package-management/archives.md). Verification does not install or open the application.

The package runs its business service without `@anybox/host`, `@anybox/distribution` or Claude Agent. Install this application and its dependencies, including the `@nya/core` peer, then use:

```sh
anybox-harness-server init "Owner device"
anybox-harness-server serve
```

`init`, `recover-access [name]` and `new-identity [name]` operate on the configured database while the daemon is stopped. They print the identity and one newly issued token once. `init` refuses an already initialized identity; recovery issues another token without changing identity; `new-identity` changes identity and revokes all old tokens. `--help` and `-h` return before configuration or resource initialization.

The standalone CLI defaults to `127.0.0.1:3001`. `ANYBOX_HARNESS_BIND`, `ANYBOX_HARNESS_PORT` (with `ANYBOX_WEB_PORT` fallback), `ANYBOX_HARNESS_NAME`, `ANYBOX_HARNESS_DATABASE`, `ANYBOX_PROJECTS` and existing Models/Computer configuration retain their meanings. The programmatic parser retains port `0` as its default. The CLI reports its URL and identity, emits the existing IPC `{ type: 'ready', instanceId, url }` shape, and joins cleanup on SIGINT/SIGTERM. This new command serves Harness alone. The distribution's existing `harness-server` command keeps its current application composition and behavior.

The public `createStandaloneHarnessServer(config, options)` API is available from the package root or `@anybox/app-harness/server`. It creates one Nya root and returns the current identity/access service, business `api`, URL, readiness, `prepareClose()` and idempotent `close()`. `options` includes the business runtime options and optional `host`/`name`. Embedded integrations use `createHarnessServerRuntime(root, config, options, integration)` on their existing root. `harnessServerApplication()` adds Anybox registration, stop protection and explicit activity/access dependencies around that same assembly. Business startup itself requires neither `app.activity` nor `host.access`.

The application owns its HTTP listener and authentication. `GET /api/v1/instance` requires a Bearer token; business requests additionally require `X-Anybox-Instance-Id`. Canonical business routes remain `/api/v1/apps/agent/*`, and the existing Models/Prompts/Tools/Agents/Projects/Sessions/Runs/Changes aliases remain supported. Token listing, issuance and revocation remain under `/api/v1/access/tokens`. Standalone mode does not install host application management or desktop pages. Computer unit endpoints exist only under `/api/v1/apps/agent/units/unit/*` and authenticate their own unit credentials; an owner token cannot authenticate a unit.

The `harness-access` component exposes `harness.access`, depends on `local-storage`, and reuses the existing `host-access` v1/v2 migration ledger, `host_identity`, `host_access_tokens` and token format. Hosted and standalone modes can reopen the same identity and business history after the other process has stopped. They cannot open the same database concurrently. No database is split or copied. Models JSON, Vault namespaces, business migration domains, image paths and worker directory defaults remain unchanged.

`harness-http` owns business request/stream/cursor cleanup. Its optional integration source declares the actual Nya dependencies and resolves each generation's services from `deps`; the Anybox adapter supplies `app.activity`/`host.access`, and standalone supplies `harness.access`. `harness-listener` exposes `harness.listener`, depends on `harness.access`, and owns the socket and authentication subscriptions. Closing first prevents new Runs and starts HTTP drain, then joins root cleanup and retained HTTP operations together. Accepted Runs are cancelled and awaited through actual model/tool exit. Closing Harness observation leaves an independent idle Computer worker running.

The public root also exports application definitions and client/server registration factories. Role-specific and domain modules are available through the `./*` subpath export. The worker CLI remains `@anybox/app-harness/entrypoints/computer-worker-main`. Its client runtime owns connections, credentials, pairing and forwarding; SQL, directory selection, Models and system credential adapters are explicit dependencies of the roles that use them. The minimum application API does not require those providers. D0a.1 provides independent business service startup; host-only distribution, consumer-selected providers, independent desktop clients and dynamic package installation remain later work.

Run `npm run build --workspace @anybox/app-harness`, `npm run typecheck --workspace @anybox/app-harness` or `npm test --workspace @anybox/app-harness` from the repository root after building workspace dependencies. Package tests cover standalone authentication, unit credential isolation, business calls, SSE revocation, completed Run persistence, actual-exit shutdown and exclusive data ownership. The root suite additionally verifies installed-package isolation, hosted compatibility, Session, Run, Models, HTTP and worker behavior.

Browser assets are resolved relative to the installed package module and retain `/applications/harness/` and `/apps/agent/` URLs. Worker startup resolves its entry relative to this package and preserves the existing process lifetime. Component ownership and cleanup are documented in [the module manual](../../docs/modules/README.md).
